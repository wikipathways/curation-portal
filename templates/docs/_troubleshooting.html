The problems people actually run into, roughly in the order they meet them. Most come from the repository's own processing, which is stricter than PathVisio about a few attributes that PathVisio always writes but hand-edited or converted files often lack.

Problems with the file

My file is refused for having no Name or no Organism, but it has both
The file is probably in the newer GPML 2021 format, which stores the title and organism differently. The portal accepts GPML 2013a, the format WikiPathways uses. Save the pathway in that format from PathVisio and upload it again.
A group has no stacking order (Group stacking order)
In every group, such as a complex, at least one member needs a ZOrder on its <Graphics>. Without it the repository's converter cannot draw the group, so no diagram or draft page is made and publishing fails later. Opening the file in PathVisio and saving it again adds the missing values.
A group inside another group
The repository's converter refuses nested groups outright, with or without stacking order, and the portal does not check for them yet. The repository's processing fails and no draft page appears. Flatten the groups (ungroup the inner one) and upload again.
Lines without a thickness (Interaction line thickness)
Every interaction needs a LineThickness on its <Graphics>, or the repository's metadata step fails, and with it the identifier table, the reference list and the draft page. Saving the file from PathVisio adds it.
Empty citation IDs (Empty citation IDs)
A literature reference with an empty ID. The repository patches it, but it is the most common reason its metadata step fails. Fill in the PubMed ID or DOI, or delete the empty reference.

Problems submitting

"GitHub rejected your authorisation"
The permission you gave the portal on GitHub was withdrawn, or has lapsed after a long time unused. You are signed out; sign in again. If writes still fail after that, remove the portal under GitHub › Settings › Applications and sign in once more to authorise it afresh.
{% if submit_identity == 'fork' %}
"GitHub did not accept the change" right after the repository changed
Before each submission the portal brings your fork up to date with the repository. GitHub can refuse that update when the repository's recent changes include its own automation files, because changing those needs a permission the portal does not ask for. Your fork is then left behind and the submission can fail. Open your fork on GitHub, press Sync fork and then Update branch, and submit again.
{% endif %}
"This pathway is checked out by …"
Someone else has an update of this pathway open. Only one edit of a pathway can be open at a time; try again once theirs is finished.
Too many submissions
Each account can open a limited number of pull requests per hour, to stop accidental retry loops. Nothing is lost: wait a while and upload again. Uploading a correction to an existing pull request is not limited.

Problems during review

{% if pipeline_mode %}
"No draft page yet"
Approval needs the draft page the repository builds while processing the pull request, because its publish workflow cannot run without it. If the processing is still running (see how long things take), wait and try again. If it failed, the Automated checks panel says so with a link to the failing run; the file almost always has one of the problems listed above, and the submitter fixes it and uploads a revision.
Not published
The submission was approved but the repository never reported a publication. Open the publish run linked from the review. Approving again removes and re-applies the accepted label, which starts a fresh run. If the pathway was published some other way, record its WPID in the Record the published WPID box instead.
{% endif %}
"The pathway changed on the main branch after this update was made"
Someone changed the published pathway while this update was waiting. An update replaces the whole file, so approving it would undo their change, and the portal refuses. The submitter downloads the current version from the Update existing form, redoes the edit on it and uploads it again; it lands on the same pull request.
"This pull request changes other files too"
Only the pathway may be published, so approval is refused while the pull request carries anything else. The usual cause is a fork that has drifted: commits on the submitter's fork that the repository does not have were carried into the pull request. On GitHub, open the fork, use Sync fork to discard the fork's own commits (if they are not needed), and submit the pathway again as a new pull request. Since the portal now checks forks before submitting, this mostly affects older pull requests and ones opened on GitHub.
"has a new commit since this page was loaded"
Someone pushed to the pull request while you were reviewing it. Reload the page and look at the new version before approving.
