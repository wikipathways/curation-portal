Curators are a configured list of GitHub accounts. Signed in as one, the header shows a Curator badge, the queue becomes the Curation queue, and review pages gain the checklist controls and the decision buttons. Everyone else can read every review but not change it.

The queue

The tabs filter by state; Assigned to me lists the unfinished reviews you lead. Each card shows the pathway's name, organism, age and assignee, a summary of the automated checks and a small diagram. Open full review opens the page where the work is done.

On GitHub, not in the portal lists open pull requests that change pathway files but were not made through the portal, for example from the PathVisio plugin. Adopt builds a review from one and posts a short comment on the pull request. An adopted pull request is reviewed like any other, except that the portal cannot change its file: the author pushes fixes to it.

Working through a review

  1. Assign yourself (or someone else) with Assign reviewer, so others know who is leading it. Any curator can still act on it.
  2. Read the automated checks and the diagram. For an update, start from what changed.
  3. Answer the checklist. Mark each item Pass, Fail or N/A. Every item starts unanswered and only you set it. Required items carry a dot. Under an item, Automated check says what the portal or the repository found and what it suggests; read it as a hint, not an answer. An item marked N/A never blocks approval. For an update, the hint says when the edit did not touch an item.
  4. Decide. Approve becomes available when every required item is marked Pass; until then, hovering over it names the items still to do.

When approval is refused

The portal refuses to approve in a few situations, each of which would publish the wrong thing:

  • The pull request changed after you loaded the page. Approval applies to the version you looked at. Reload and check the new one.
  • The pathway changed on the main branch after the update was made. Approving would undo that change. The submitter redoes the edit on the current version.
  • The pull request changes other files too. Only the pathway may be published. Usually the submitter's fork has drifted (see unexpected files).

  • The draft page is not built yet. The repository's publish workflow needs it. If the repository's processing failed, the submitter has to fix the file; if it just finished, try again in a few minutes.

Recording a WPID by hand

Normally there is nothing to do: the repository announces the WPID it assigned a minute or so after its publish workflow runs, and the review becomes Published by itself. Only when that visibly fails (the review says Not published, or the publish workflow finished ten minutes ago and no WPID has arrived) does the review offer a Record the published WPID box. Once you have confirmed on GitHub or {{ site_host or 'the site' }} which identifier the repository assigned, enter it there to close the review.
